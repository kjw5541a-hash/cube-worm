# 큐브 지렁이 설계

- 작성일: 2026-10-06
- 상태: 설계 승인. 1~4단계 구현 계획 `docs/superpowers/plans/2026-10-07-cube-worm-stage1-4.md`
- 저장소: `~/games/cube-worm`, 화면 제목 "큐브 지렁이" (둘 다 임시 이름)

## 목표

2D 스네이크를 세 축으로 넓힌 모바일 게임이다. 둥근 정육면체 마디가 이어진 지렁이가 흙 상자 속을
앞뒤·좌우·위아래로 돌아다니며 벌레를 먹는다. 카메라는 쿼터뷰로 고정하고, 필요할 때 맵을 90°씩 돌린다.

사용자가 강조한 것은 "매우 자연스럽고 부드럽게"다. 판정은 칸 단위로 하지만, 화면의 몸은 끊김 없이
미끄러지고 꺾이는 곳에서는 곡선으로 휜다.

성공 기준:

1. 폰 브라우저에서 몸이 500마디여도 60fps.
2. 몸이 튀거나 끊기지 않는다. 걸음이 바뀌는 순간 앞뒤로 모든 마디의 위치와 방향이 이어진다(테스트로 고정).
3. 화면에 보이는 몸은 언제나 실제 판정 칸과 일치한다(테스트로 고정).
4. 높낮이를 헷갈려서 죽는 일이 없다(3단계 플레이로 판단).

## 플랫폼

- Godot 4.7.2 / GDScript. 세로 720×1280 기준, 더 긴 화면은 세로로 늘려 쓴다(stretch `canvas_items`, aspect `expand`).
- 렌더러는 처음부터 Compatibility 로 둔다. 웹 빌드는 설정과 무관하게 Compatibility 로 돌기 때문에,
  데스크톱에서 보는 화면과 폰 화면을 같게 하려는 것이다.
- GitHub Pages 웹 배포가 먼저다. 안드로이드 앱은 나중에 따로 정한다.
- 물리 엔진은 쓰지 않는다. 판정은 정수 칸 논리로만 한다.

## 1. 규칙

- **상자**: 8×8×8 칸(조정값). 칸 좌표는 `Vector3i`, 각 축 0~7. 높이는 Godot Y 축이다(사용자는 "z축"이라 부른다).
- **시작**: 지렁이 3마디 일직선. 머리 (4,4,4), 몸 (5,4,4)·(6,4,4). 머리는 −X(회전 0단계에서 화면 ↖)를 본다.
  멈춘 채 기다리다가 첫 방향 입력으로 출발한다.
- **속도**: 처음 초당 3칸, 벌레 한 마리마다 +0.1칸, 최대 초당 6칸(30마리째에 도달).
- **벌레**: 항상 3마리가 있다. 시작할 때 빈 칸에 무작위로 3마리를 두고, 한 마리를 먹을 때마다 빈 칸 하나에
  새로 생긴다. 빈 칸은 지렁이·바위·다른 벌레가 없는 칸이다. 빈 칸이 모자라면 있는 만큼만 둔다.
- **먹기**: 1점. 그 걸음에 꼬리가 제자리에 남아 한 마디 길어진다. 속도가 오른다.
- **바위**: 판마다 무작위로 8개. 시작 지렁이 칸에서 체비쇼프 거리 2 이내에는 두지 않는다.
- **죽음**: 머리가 들어가려는 칸이 상자 밖, 바위, 자기 몸이면 게임오버다. 단, 현재 꼬리 칸은 그 걸음에
  비워지므로 들어가도 된다(꼬리 따라가기). 먹는 걸음에는 꼬리가 남지만 그때 머리는 벌레 칸으로 들어가므로
  꼬리 칸과 겹칠 수 없다. 그래서 "현재 꼬리 칸은 항상 통과" 하나로 규칙이 정리된다.
- **최고 기록**: 점수 하나만 기기에 저장한다(`user://save.cfg`). 서버 없음.

## 2. 화면 흐름

- **타이틀**: 뒤에 실제 게임 장면(상자 속에서 제자리 꿈틀대는 지렁이, 벌레, 바위)을 깔고, 위에 제목,
  최고 기록, 시작 버튼, 빌드 버전.
- **게임**: 위쪽 HUD(점수, 회전 ⟲ ⟳, 일시정지), 가운데 흙 상자, 아래 컨트롤러. HUD 는 노치(안전 영역)를 피한다.
- **게임오버**: 점수, 신기록이면 표시, 다시하기.
- **일시정지**: HUD 버튼 또는 앱이 백그라운드로 가면 자동. 계속하기, 그만하기(타이틀로).
- 소리는 v1 에 없다.

## 3. 조작

### 컨트롤러

화면 아래쪽에 둔다.

```
            [ ▲ ]
     [ ↖ ]   /\   [ ↗ ]
            <  >          가운데 마름모 = 상자 윗면과 같은 모양
     [ ↙ ]   \/   [ ↘ ]
            [ ▼ ]
```

- 마름모는 카메라 투영에서 계산해 그린다. 그래서 상자 윗면과 기울기·비율이 항상 같다
  (정확한 등각에서 내각 60°/120°, 가로:세로 = √3:1).
- 수평 4방향 버튼은 마름모 네 변 바깥에, 위아래 버튼은 마름모 위·아래에 둔다. 6방향은 화면에서 정확히 60° 간격이다(4절).
- 판정은 컨트롤러 중심에서 본 각도로 한다. 60° 부채꼴 6개로 나눠서, 버튼 사이를 눌러도 가장 가까운 방향이 된다.
  마름모 안쪽 터치는 무시한다.
- 손가락이 닿는 순간 한 번 입력된다(뗄 때가 아니다). 누른 채 다른 방향으로 미끄러져도 새 입력이 아니다.
  여러 손가락은 닿은 순서대로 처리한다.
- 누르면 그 버튼이 즉시 빛난다.

### 화면 기준 방향

버튼은 화면 기준이다. ↗ 는 언제나 "지금 화면에서 ↗ 로 보이는 축 방향"이다. 맵을 돌려도 버튼 위치와
의미는 그대로고, 실제로 움직이는 월드 축만 바뀐다.

화면 방향 → 월드 축 변환은 `camera_rig.gd` 한 곳만 맡는다. 이 계산이 두 곳에 있으면 회전 뒤에 서로
어긋난다(blockbox 교훈). 변환은 버튼을 누른 순간의 시점으로 한다. 회전 중이면 회전이 끝난 뒤의 시점(목표 시점)으로 한다.

### 입력 큐

- 최대 2개를 미리 받는다. 꽉 차 있으면 새 입력은 버린다.
- 비교 대상과 같거나 정반대인 입력은 무시한다. 비교 대상은 큐의 마지막 입력이고, 큐가 비었으면 지금 칸의
  확정된 출구 방향이다(6절).
- 대기 중(출발 전)에는 목 쪽 방향만 무시하고, 나머지 다섯 방향 중 하나로 출발한다.

### 키보드 (PC 테스트용)

`Q`↖ `W`▲ `E`↗ / `A`↙ `S`▼ `D`↘ — 컨트롤러와 같은 육각 배치. 회전은 `←` `→`, 일시정지는 `Esc`.

## 4. 공간과 시점

- 칸 (x, y, z) 의 중심은 월드 (x+0.5, y+0.5, z+0.5) 이다. 상자는 (0,0,0)~(8,8,8).
- **카메라**: 직교 투영, 정확한 등각. 내려다보는 각 35.264°(= atan(1/√2)), 좌우 45° + 90°·k (k = 0~3).
  이 각도에서만 6방향이 화면에서 정확히 60° 간격으로 보인다. 원근 투영은 화면 위치마다 축 방향이 틀어져
  버튼 매핑이 깨지므로 쓰지 않는다.
- 정육면체 상자는 화면에서 정육각형으로 보인다. 상자 전체가 항상 화면 안에 있다(화면 폭에 맞춤).
  따라가기·확대는 없다. 회전 중간 각도의 상자는 45° 자세보다 작게 보이므로 잘리지 않는다.
- **회전**: HUD 버튼 2개(키보드 ← →), 90°씩 0.3초 ease in-out. 대기·진행 중에만 되고, 도는 동안 게임 시간이 멈춘다.
  빠르게 두 번 누르면 목표 각도를 누적한다. 진행 중인 중간값에 90°를 더하면 화면 각도가 회전 단계와
  영구히 어긋난다(blockbox 교훈).

## 5. 땅속 보여주기

쿼터뷰에서는 "한 칸 위"와 "대각선으로 한 칸 뒤"가 화면의 정확히 같은 자리에 찍힌다. 다섯 장치로 푼다.

1. **단면 상자**: 개미집 관찰 상자처럼 먼 쪽 벽 2개와 바닥에만 흙 단면을 그린다. 상자 메시의 면을
   안쪽으로 뒤집고 뒷면 컬링을 켜면, 어느 회전 각도에서든 가까운 벽 2개와 윗면이 저절로 안 그려진다.
   셰이더가 높이별 지층 띠(깊을수록 짙은 갈색), 옅은 칸 격자, 벽 위 가장자리의 풀 띠를 그린다. 텍스처는 없다.
2. **머리 층 판**: 머리의 화면상 높이(보간된 Y)에 반투명 격자판 한 장을 둔다. 상자 안쪽 8×8 전체를 덮는다.
   - 판 아래 물체는 판 너머로 흐리게, 위 물체는 선명하게 보이고, 같은 층 물체는 판이 가운데를 가른다.
   - 판의 네 가장자리가 그 높이의 벽 위치를 보여준다. 가까운 쪽 벽은 그려지지 않지만 경계는 보인다.
   - 판이 먼 벽과 만나는 선이 바닥·천장까지 남은 거리를 보여준다.
3. **벌레 고리와 기둥**: 판 위, 벌레와 같은 (x, z) 자리에 고리를 그리고, 고리에서 벌레까지 세로 기둥을 세운다.
   같은 층이면 기둥 길이가 0 이 되어 고리만 남는다. 판이 연속으로 움직이므로 기둥도 연속으로 줄고 는다.
4. **높이 색**: 깊을수록 어둡게. 맨 위 100% → 맨 아래 약 60%(조정값). 월드 Y 로 계산하므로 오르내리는
   지렁이의 색도 연속으로 변한다.
5. **비침**: 머리와 벌레가 몸이나 바위에 가려지면 윤곽이 비쳐 보인다. 깊이 검사를 뒤집은(`depth_test_inverted`)
   반투명 두 번째 패스로 그려서, 가려진 부분에만 칠해진다. 1단계 스파이크(2026-10-06)에서 웹 Compatibility
   (Chrome WebGL2)로 동작을 확인하고, 스텐실 대신 이 방식으로 정했다.

넣지 않는 것: 벽면 투영(화면이 복잡해짐), 그림자(판·기둥과 역할이 겹치고 모바일 비용이 듦),
앞 칸 위험 경고(높이 착각으로 죽는 일이 잦으면 그때 넣는다).

## 6. 움직임

### 경로 모델

- **걸음**: 머리가 한 칸 나아가는 시간. 길이는 1 / 속도.
- **진행값 p**: 단조 증가하는 실수. 정수 부분 k 는 머리가 지나는 칸의 기록 번호, 소수 부분 α 는 그 칸 안의
  진행률이다(0 = 입구 면, 1 = 출구 면).
- 머리가 지나온 칸 기록 `H[k]` 마다 입구 방향과 출구 방향을 저장한다.
- **마디 j**(머리 = 0)는 진행값 p − j 에 놓인다. 즉 자기가 차지한 칸 `H[k−j]` 안에, 모든 마디가 같은 α 로
  있다. 그래서 화면의 몸은 언제나 판정 칸 안에 있다.
- **칸 안 경로**:
  - 직진: 입구 면 중심 → 출구 면 중심 직선.
  - 꺾임: 두 면 중심을 잇는 반지름 0.5 의 4분원. 원의 중심은 두 면이 만나는 모서리의 중점
    (칸 중심 − 0.5·입구 방향 + 0.5·출구 방향)이다. 각도는 α 에 비례한다. 위아래로 꺾일 때도 같다.
  - 꺾이는 칸의 경로 길이는 π/4 로 직진보다 짧다. 칸마다 같은 시간이 걸리므로 곡선에서는 그만큼 천천히 지나간다.
    마디 간격도 곡선에서 조금 좁아져 안쪽은 겹치고 바깥은 벌어진다. 마디 벌레처럼 보인다.

### 걸음 이벤트

α 가 1 에 닿는 순간(머리가 출구 면을 넘는 순간) 차례대로:

1. 다음 칸 = 현재 칸 + 출구 방향. 이 방향은 지난 걸음 이벤트에서 이미 정해져 있다.
2. 충돌 검사(1절 죽음 규칙). 실제 검사는 걸음 이벤트보다 먼저 한다. 다음 칸이 막혀 있으면 머리 앞면이 장애물 면에
   닿는 진행률(1 − 머리 크기/2, 약 0.52)에서 멈추고 죽는다. α = 1 까지 가면 머리가 장애물에 반쯤 박혀 보인다
   (계획 검증 중 발견). 출구는 칸에 들어설 때 이미 정해지므로, 어느 시점에 검사해도 결과는 같다.
3. 다음 칸에 벌레가 있으면 먹는다. 꼬리를 남기고(마디 하나 추가), 새 벌레를 만들고, 속도를 올린다.
4. 머리를 다음 칸으로 옮기고, 큐에서 방향 하나를 꺼내 새 칸의 출구를 정한다. 큐가 비었으면 직진한다.

입력이 실제 꺾임으로 나타나는 것은 다음 걸음 이벤트부터다. 기다리는 시간은 최대 한 걸음
(시작 속도 0.33초, 최고 속도 0.17초)으로 클래식 스네이크와 같은 수준이다.

대기 상태에서는 α = 0 이다(모든 마디가 칸 입구 면에 있다). 첫 입력은 큐를 거치지 않고 바로 머리 칸의
출구가 되며 출발한다. α = 0 이므로 출구를 그 자리에서 정해도 경로가 튀지 않는다.

### 시간

- `_process` 에서 프레임마다 p 를 `속도 × delta` 만큼 올린다. 물리 프레임을 쓰지 않는 것은 화면 주사율과
  어긋나 떨림이 생기기 때문이다.
- 한 프레임에 p 가 1/3 을 넘게 오르지 않게 자른다. 프레임이 밀리면 잠깐 느려질 뿐, 화면에 안 보인 채
  한 칸을 건너뛰어 죽는 일은 없다.
- 일시정지, 회전 중, 게임오버 뒤에는 p 가 멈춘다.

### 자세

- 앞 = 경로 접선 방향.
- 수평으로 갈 때 윗면은 항상 +Y 다(머리의 눈이 똑바로 선다).
- 수직으로 갈 때는 직전 수평 자세에서 피치만 한 자세다. 올라갈 때 윗면은 직전 진행 방향의 반대,
  내려갈 때 윗면은 직전 진행 방향이다.
- 꺾이는 칸 안에서는 입구 자세 → 출구 자세를 α 로 보간한다.
- 몸통 마디도 같은 규칙을 따른다.

### 반응과 연출

- **예고 동작**: 버튼을 누르는 즉시 머리가 그 방향으로 살짝(약 15°, 조정값) 고개를 돌린다. 큐의 첫 입력
  방향을 본다. 실제로 꺾이기 시작하면 경로 자세로 자연스럽게 합쳐진다.
- **꿈틀거림**: 머리에서 꼬리로 흐르는 약한 굵기 파동(지렁이 연동운동). 진폭 약 ±5%(조정값). 시각 효과일 뿐 판정과 무관하다.
- **자람**: 먹은 걸음에 새 마디가 원래 꼬리 칸에서 크기 0 → 1 로 한 걸음 동안 부풀어 오른다.
  판정 길이는 그 즉시 늘어난다.
- **꼬리**: 마지막 3마디를 점점 작게 그린다(조정값).
- **먹기**: 벌레가 머리 쪽으로 빨려 들며 작아지고(걸음의 앞쪽 절반), 불룩한 덩어리가 몸을 따라 꼬리까지
  흘러간다. 시각 효과일 뿐이다.
- **속도 변화**: 연속으로 바뀌어 걸음 사이에서 튀지 않는다.
- **죽음**: 머리가 부딪힌 면에서 찌그러지며 멈추고, 화면이 짧게 흔들리고, 1초 뒤 게임오버 화면이 나온다.

## 7. 그래픽

### Blender 에셋 (MCP)

- 에셋마다 Blender 파이썬 스크립트 하나를 `assets/blender/<이름>.py` 에 둔다. 스크립트가 원본이다.
- 작업 흐름: MCP `execute_blender_code` 로 사용자의 Blender 에서 실행 → `look` 으로 렌더를 보며 고침 →
  `assets/models/<이름>.glb` 로 내보냄.
- MCP 에서는 전용 씬(`cube_worm`)에서만 작업한다. 사용자가 열어 둔 다른 씬은 건드리지 않는다.
- AI 생성(`generate_3d`)과 외부 에셋 라이브러리는 쓰지 않는다. 둥근 정육면체 스타일은 코드 조립이 더 정확하고
  크레딧도 들지 않는다.
- 에셋 메이커 스킬은 참조 이미지가 필수라 쓰지 않는다. 좌표 규칙은 맞춘다: 1단위 = 1칸, 정면 Godot −Z,
  metallic 0, 단색 재질, 텍스처 없음. 다만 원점은 바닥이 아니라 칸 중심이다(모든 에셋이 칸 한가운데 놓인다).

| 에셋 | 모양 | 삼각형 상한 |
|---|---|---|
| `worm_segment` | 둥근 정육면체. 분홍빛 지렁이 색 | 300 |
| `worm_head` | 마디보다 조금 큰 둥근 정육면체 + 눈 두 개 + 입. 눈으로 진행 방향이 읽힌다 | 1500 |
| `grub` | 통통한 굼벵이. 작은 둥근 정육면체 3~4개를 C 자로 이음. 크림·노랑 | 1000 |
| `rock` | 울퉁불퉁한 둥근 돌, 칸을 거의 채우는 크기. 회색. 놓을 때 무작위 90° 회전 | 500 |

- 지렁이(머리·마디)와 벌레는 시안을 2~3개씩 렌더해 사용자가 고른다.
- 마디 번호 3(머리 = 0)은 밝은 띠(지렁이 환대)로 칠한다. MultiMesh 인스턴스 색으로 칠하므로 에셋을 따로 만들지 않는다.

### Godot 코드로 그리는 것

흙 상자(셰이더), 머리 층 판, 벌레 고리·기둥, 컨트롤러, 배경(어두운 갈색 단색).

### 공용 셰이더

- 지렁이·벌레·바위가 셰이더 하나를 같이 쓴다. 게임이 GLB 를 읽을 때 재질의 albedo 색만 꺼내고 이 셰이더로
  바꿔 끼운다. 높이 색을 모든 물체에 똑같이 적용하고 비침을 머리·벌레에 붙이려는 것이고, glTF 재질을 Compatibility 에서
  그대로 쓰면 모양이 달라지는 문제(3DBlockBreaker: 금속이 검게 죽음)도 피한다.
- 색 = 에셋 색 × 높이 색. 부드러운 기본 조명(방향광 하나 + 환경광), 그림자 없음.
- 벌레는 은은하게 빛난다(발광 + 느린 깜빡임). 깊고 어두운 층에서도 보이게 하려는 것이다.
- 벌레의 꼼지락 대기 동작은 코드로 한다. Blender 애니메이션은 쓰지 않는다.

### 첫 등장 버벅임 방지

Compatibility 렌더러는 재질 조합을 처음 그릴 때 셰이더를 컴파일한다. 타이틀 화면의 실제 게임 장면이 모든
재질과 효과(비침, 먹기, 자람 포함)를 미리 한 번씩 그린다. 숨긴 노드(`visible = false`)는 그려지지 않아
컴파일도 안 되므로, 안 보이게 하려면 크기를 아주 작게 줄인다(3DBlockBreaker `_WARM_SCALE` 방식).

## 8. 코드 구조

파일 하나에 책임 하나. 규칙 파일은 노드에 의존하지 않는다(`RefCounted`). 헤드리스 테스트로 전부 검사한다.

| 파일 | 책임 |
|---|---|
| `scripts/tuning.gd` | 조정값 전부(상자 크기, 속도, 바위·벌레 수, 회전 시간, 연출 세기) |
| `scripts/worm.gd` | 칸 기록과 입·출구 방향, 걸음, 자람, 몸 칸 집합 |

| `scripts/worm_path.gd` | 순수 수학: 칸 기록 + p → 마디별 위치·자세 |
| `scripts/camera_rig.gd` | 회전 단계와 트윈, 화면 방향 → 월드 축 변환(단독 소유), 축의 화면 투영 |
| `scripts/controller.gd` | 마름모와 버튼을 카메라에서 계산해 그림, 부채꼴 판정, 키보드 |
| `scripts/worm_view.gd` | 머리 메시 + 몸 MultiMesh, 연출 |
| `scripts/field_view.gd` | 흙 상자, 바위, 벌레, 머리 층 판, 고리·기둥 |
| `scripts/hud.gd` | 점수, 회전·일시정지 버튼 |
| `scripts/main.gd` | 화면 흐름(타이틀/게임/일시정지/게임오버) |

다시 만들 필요가 없다.

## 9. 테스트

- **보이는 몸 = 판정 칸**: 시드를 고정한 무작위 입력으로 수천 걸음을 진행하며, 프레임마다 모든 마디의 위치가
  자기 칸(닫힌 정육면체) 안에 있는지 검사한다.
- **연속성**: 걸음 이벤트 직전(α → 1)과 직후(α = 0)의 마디 위치·자세가 같은지(오차 1e-4).
- **버튼 = 화면 방향**: 회전 4단계 × 버튼 6개 전부, 실제 Camera3D 로 월드 축을 투영한 화면 각도가 버튼 각도와
  1° 안에서 같은지. 관계만 보는 테스트는 표 전체가 뒤집혀도 통과하므로 실제 카메라와 대조한다(blockbox 교훈).
- **마름모 = 상자 윗면**: 마름모 꼭짓점이 상자 윗면 네 모서리의 투영과 배율을 빼고 같은지.
- **규칙**: 벽·몸·바위 충돌, 꼬리 따라가기 허용, 같은·반대 방향 무시, 큐 최대 2, 먹기 → 점수·길이·속도,
  속도 상한 6, 벌레가 항상 3마리이고 빈 칸에만 생김, 바위가 시작 영역을 피함.
- **시간**: 큰 delta 한 번에 p 가 1/3 넘게 오르지 않음. 일시정지·회전 중 p 정지.
- **글자**: 화면 문자열의 글자가 폰트 부분집합에 다 있는지.
- 실패한 assert 는 헤드리스 Godot 을 멈춰 세우므로 러너가 시간 제한으로 감싼다(blockbox `run_tests.sh`).
- 고친 뒤 변이 테스트로 검사가 실제로 잡는지 확인한다.

## 10. 만드는 순서

단계마다 브랜치 하나, 병합하면 바로 삭제한다.

1. **스파이크**(코드는 버림): 비침이 웹 Compatibility 에서 되는지. 2026-10-06 계획 작성 중에 끝냈다(5절 5번).
2. **규칙**: `tuning`·`worm`·`field`·`game` + 테스트.
3. **첫 플레이(데스크톱)**: 임시 도형, `worm_path`(곡선·자세·자람·꿈틀거림), 땅속 보여주기 다섯 장치, 컨트롤러와 회전.
   컨트롤러는 터치와 키보드가 한 파일이라 같이 만든다. 개발용 fps 표시와 성능 확인용 시작 옵션(웹은 주소 끝 `?perf`,
   데스크톱은 `-- --perf`: 몸 500마디, 바위 없음)도 여기서 넣는다. 죽으면 "탭하면 다시 시작"(타이틀·게임오버 화면은 6단계).
   여기서 판단한다: 3D 가 읽히나, 재밌나, 상자 크기와 속도가 맞나.
4. **폰**: 웹 배포(브랜치마다 Pages, 화면에 날짜·브랜치·커밋)와 폰 플레이 확인. GitHub 저장소 생성과 공개 여부는 이때 묻는다.
5. **그래픽**: Blender 에셋(시안 → 선택 → 최종), 공용 셰이더, 먹기·죽음 연출.
6. **마무리**: 타이틀(라이브 장면 + 셰이더 미리 굽기), 게임오버, 최고 기록, 일시정지.

3단계를 앞에 둔 이유: 가장 큰 위험은 "쿼터뷰에서 3D 가 읽히는가"다. 그래픽에 시간을 쓰기 전에 확인한다.

## 11. 플레이로 판단할 것

조정값은 전부 `tuning.gd` 에 있다: 상자 크기 8, 속도 3 → 6(+0.1), 바위 8, 벌레 3, 회전 0.3초,
높이 색 최저 60%, 예고 동작 15°, 꿈틀거림 ±5%, 꼬리 크기. 땅속 장치로 충분히 읽히지 않으면 앞 칸 위험 경고를 검토한다.
